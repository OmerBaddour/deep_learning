The HPC peak-FLOP/s equation, factor by factor

Peak floating-point throughput is one long multiplication where the units cancel until only FLOP/s survives. This companion now has four parts: the equation itself, a look inside your i9's datapath to see where the 16 FLOPs/cycle physically come from, a guide to researching chip internals yourself, and a runnable assembly demo that pins one core to its peak.

That cancellation is the sanity check — if your units don't reduce to FLOP/s, a factor is upside-down (this is exactly the instinct behind your "shouldn't it be sockets/core?" question below).

02 What hides inside FLOPs / cycle

This is the factor that trips everyone, and the one the Task-1b prompt fumbled by listing "(2 for FMA) × (2 for mul+add)" as if they were independent. They aren't. One core does this much per cycle:

4
SIMD lanes
An AVX2 register is 256 bits. At fp64 (8 bytes) that's 256/64 = 4 numbers processed side by side. fp32 → 8.
2
FMA units
Skylake/Coffee-Lake cores have two 256-bit fused-multiply-add ports (Port 0 & Port 1), so two FMA instructions issue per cycle.
2
FLOPs / FMA
One fused multiply-add computes a×b+c — a multiply and an add, counted as 2 FLOPs.
16
= FLOPs / cycle
4 × 2 × 2, at fp64. This is the whole "work/cycle" box above, for one core.

So the prompt's arithmetic (4×2×2 = 16) was right; only its labels were scrambled. The honest reading: lanes × FMA-ports × (mul+add). FMA is not a bonus multiplier stacked on a separate "mul+add" — FMA is the mul+add. See the two FMA ports physically, in tab 02 →

04 Your four questions

Is a node basically one machine? yes

Yes. A node is one independent computer: one motherboard, one OS image, its own RAM. A supercomputer is thousands of nodes wired together by a fast network. The equation multiplies by nodes first because that's the coarsest unit of "how much hardware."

Are sockets the Linux-networking kind? name collision

No — and this is the single most common confusion, purely because one word got reused for two unrelated things.

Here, a socket is the physical CPU socket: the mechanical slot on the motherboard where a processor package clamps in. "2-socket server" = a board with two physical CPUs. It is hardware you could cut yourself on.

The ~60k-simultaneous figure you're thinking of is network sockets — an OS abstraction for a TCP/UDP connection endpoint, bounded by the 16-bit port space (~65,535 ports). Totally different concept, totally unrelated to FLOP/s. Same five letters, no shared meaning.

How to think about cores / socket — isn't it backwards? it's per-socket

It reads cores per socket, and that direction is correct. A physical CPU package (socket) physically contains N cores etched onto the same die — your i9 is 8 cores in 1 socket, so cores/socket = 8. The containment runs socket → cores, so the ratio is cores per socket.

Your instinct to flip it to sockets/core comes from the networking meaning again — there, many connection-sockets do share one core while it waits on I/O. But a hardware socket is a physical object that holds cores; it can't be time-shared across them. Trust the unit-cancellation: you need cores/socket for socket to cancel against sockets/node. Flip it and the units no longer reduce to FLOP/s.

Does cycles/second just mean each core's frequency? yes

Exactly. Cycles/second is clock frequency — 2.3 GHz = 2.3×10ⁿ cycles every second, per core. A "cycle" is one tick of the clock; each tick, a core can retire up to FLOPs/cycle of work. You don't jump from cores/socket to cycles/second — they're two separate independent factors that both get multiplied in. Reading the chain as English: "8 cores, each ticking 2.3 billion times a second, each tick doing 16 FLOPs."

02 Inside one i9 core — where 16 FLOPs/cycle live

The peak equation ends in "16 FLOPs/cycle" as if it were a single fact. It isn't — it's a physical layout. Like the MIPS datapath you studied, this is a schematic: an instruction enters at the top, flows down through the front-end, gets scheduled, and is executed on one of eight ports. The whole "16" comes from just two of those eight ports. This is a Skylake-client core (the microarchitecture Coffee Lake reuses); it is out-of-order and superscalar, so unlike the strictly-in-order classroom MIPS pipeline, many instructions are in flight at once.

One 256-bit FMA unit, one clock tick

The register is 256 bits wide. At fp64 that's 4 independent lanes, and the unit computes a×b+c in every lane simultaneously — this is the SIMD ("single instruction, multiple data") idea made physical.

2 FMA ports × 4 lanes × 2 FLOPs (mul+add) = 16 fp64 FLOPs / cycle
× 8 cores × 2.3×10ⁿ cycles/s = 294 GFLOP/s

How to read it against classroom MIPS

The single-cycle MIPS datapath you saw draws one instruction's whole journey — PC → instruction memory → register file → ALU → data memory → write-back — as one straight wire, because that machine does exactly one instruction at a time. This chip keeps the same skeleton (fetch → decode → execute → write-back) but widens every stage: it fetches/decodes several instructions per cycle, keeps ~224 in flight, and has eight parallel ALUs/AGUs instead of one ALU. The "ALU" box of MIPS has, in effect, been photocopied eight times into the port row — and two of those copies are the wide FMA units that make the FLOP/s number.

The key mental shift: in MIPS, "what happens per cycle" is one operation. Here it's "up to 8 µops issued, and on the two FMA ports each µop is 4 lanes × (mul+add) = 8 FLOPs." That fan-out — 1 op → 16 FLOPs — is the entire distance between the scalar Python engine and the hardware ceiling.

Every block above is a real, documented structure — the next tab shows you exactly which reference to open to confirm each number (port assignments, ROB size, lane widths) yourself.

03 How I found "2 FMA ports" — and how you can

You asked where the "2 FMA ports on Coffee Lake" number comes from, and why hardware facts feel so much more scattered than, say, a Stack Overflow answer. The honest reason: CPU internals have a small number of authoritative primary sources and a lot of low-quality secondary noise on top. Software feels better-documented because the primary source (the code, the RFC) is usually one click away. For hardware, the trick is knowing the four or five primary sources by name and going straight to them. Here's the exact path I took.

Map the marketing name to a microarchitecture

The number on the box (i9-9880H) is a product. Performance facts live one level down, at the microarchitecture. So step one is always: "what core is inside this?" Search i9-9880H wikichip or read Intel ARK. Answer: it's a Coffee Lake product, and Coffee Lake reuses the Skylake (client) core unchanged. That word — "Skylake" — is the key you look everything else up under. This is the single step most people skip, and it's why searching the product name directly returns junk.

Go to the microarchitecture reference, not a forum

Open WikiChip's Skylake (client) page and find the execution-engine / port diagram. It shows the scheduler feeding 8 ports and labels which units sit on each. You'll see FMA on Port 0 and Port 1. That's your "2 FMA ports," read directly off the block diagram — the same diagram I redrew in tab 02.

Confirm it with a second, independent primary source

Never trust one page for a hardware number. The gold standard is Agner Fog's optimization manuals — specifically instruction_tables.pdf. Look up VFMADD231PD for Skylake: it lists reciprocal throughput = 0.5 and ports p0 p1. "Recip throughput 0.5" literally means two per cycle — an independent confirmation of the 2 FMA ports, from measured data rather than a diagram. A third cross-check is uops.info, which auto-measures every instruction on every microarchitecture.

When you want the vendor's own words

The primary-primary source is the Intel 64 & IA-32 Optimization Reference Manual — it has the Skylake pipeline and port table straight from Intel. It's dense and not a first stop, but it's the ground truth every other source is derived from. For "how many lanes," the instruction reference for VFMADD…PD tells you it operates on 256-bit YMM registers = 4 packed doubles.

Why this feels harder than software research

It isn't your domain knowledge — it's a real structural difference, and naming it helps:

Software: the primary source (source code, the RFC, the language spec) is public and one search away, and Q&A sites like Stack Overflow sit directly on top of it.

Hardware: the primary source is a 5,000-page vendor PDF plus a handful of independent measurers (Agner, uops.info). Most web results are tertiary — forum posts and blogs summarizing summaries — so a naive search surfaces the noise. The skill isn't grinding harder; it's knowing the ~5 primary names above and jumping straight to them, exactly the way you'd jump straight to the language spec instead of a random blog.

Rule of thumb: product name → microarchitecture name → WikiChip for the picture → Agner/uops.info to confirm the number → Intel manual only to settle a dispute. Follow that order and CPU facts stop feeling like folklore.

04 See peak FLOP/s on your own hardware

This is the "watch it happen" exercise you asked for. We hand-write the exact instruction from tab 02 — vfmadd231pd on 256-bit ymm registers — in a tight loop, feed it enough independent accumulators to hide latency, time it, and divide FLOPs by seconds. On your i9 a single core should report tens of GFLOP/s (near single-core turbo × 16), against the ~2 MFLOP/s of the scalar Python engine — a factor of ~20,000×, seen live.

Why 10 accumulators? One FMA has ~4-cycle latency but the port accepts a new one every cycle. If you chain x = fma(a,b,x), each op waits 4 cycles for the previous result → you'd hit ¼ of peak. Using 10 independent running sums keeps both FMA ports busy every cycle while any one result is still cooking. This "break the dependency chain" trick is the whole game in peak-FLOP microbenchmarks.
fma_kernel.sx86-64 · AT&T syntax · AVX2+FMA · macOS/Linux
# =====================================================================
#  fma_kernel.s  —  the tightest fp64 FMA loop the Skylake core allows.
#  Computes nothing useful; its ONLY job is to keep ports 0 & 1 saturated
#  so the measured GFLOP/s approaches the hardware ceiling from tab 02.
#
#  Instruction ref (what vfmadd231pd does, lane by lane):
#    https://www.felixcloutier.com/x86/vfmadd132pd:vfmadd213pd:vfmadd231pd
#  Why 0.5 recip-throughput = 2/cycle (the "2 FMA ports" fact):
#    https://www.agner.org/optimize/instruction_tables.pdf   (search VFMADD)
#  AT&T vs Intel assembly syntax (operand order is REVERSED here):
#    https://en.wikipedia.org/wiki/X86_assembly_language#Syntax
# =====================================================================

    .text
    .globl _fma_kernel            # macOS prefixes C symbols with '_'. On Linux
                                  # use 'fma_kernel' (no underscore) instead.

# double fma_kernel(uint64_t iters);
#   arg  iters -> %rdi   (System V AMD64 calling convention: 1st int arg)
#   ret  double -> %xmm0
#   FLOPs performed = iters * 10 accumulators * 4 lanes * 2 (mul+add)
_fma_kernel:
    vbroadcastsd Lc(%rip), %ymm10   # ymm10 = [c,c,c,c], a tiny fp64 constant in all 4 lanes
    vmovapd      %ymm10, %ymm11     # ymm11 = same; we multiply ymm10*ymm11 each step

    # 10 independent accumulators, all zeroed. xorpd of a reg with itself = 0.
    vxorpd %ymm0,%ymm0,%ymm0
    vxorpd %ymm1,%ymm1,%ymm1
    vxorpd %ymm2,%ymm2,%ymm2
    vxorpd %ymm3,%ymm3,%ymm3
    vxorpd %ymm4,%ymm4,%ymm4
    vxorpd %ymm5,%ymm5,%ymm5
    vxorpd %ymm6,%ymm6,%ymm6
    vxorpd %ymm7,%ymm7,%ymm7
    vxorpd %ymm8,%ymm8,%ymm8
    vxorpd %ymm9,%ymm9,%ymm9

    testq %rdi, %rdi            # if iters == 0, skip the loop
    je    Ldone
Lloop:
    # AT&T operand order: vfmadd231pd  SRC2, SRC1, DST
    #   computes  DST = SRC1*SRC2 + DST   -> here  ymmN = ymm10*ymm11 + ymmN
    # 10 of them = 5 cycles of work on 2 ports; the next iteration's copies
    # can start before these finish, so both FMA ports stay 100% busy.
    vfmadd231pd %ymm11,%ymm10,%ymm0
    vfmadd231pd %ymm11,%ymm10,%ymm1
    vfmadd231pd %ymm11,%ymm10,%ymm2
    vfmadd231pd %ymm11,%ymm10,%ymm3
    vfmadd231pd %ymm11,%ymm10,%ymm4
    vfmadd231pd %ymm11,%ymm10,%ymm5
    vfmadd231pd %ymm11,%ymm10,%ymm6
    vfmadd231pd %ymm11,%ymm10,%ymm7
    vfmadd231pd %ymm11,%ymm10,%ymm8
    vfmadd231pd %ymm11,%ymm10,%ymm9
    decq %rdi                    # iters--
    jne  Lloop                    # loop while iters != 0
Ldone:
    # Reduce the 10 vector accumulators down to one scalar so the compiler
    # can't delete the whole loop as "dead code". Correctness of the sum
    # doesn't matter — only that the result is USED (returned).
    vaddpd %ymm1,%ymm0,%ymm0
    vaddpd %ymm3,%ymm2,%ymm2
    vaddpd %ymm5,%ymm4,%ymm4
    vaddpd %ymm7,%ymm6,%ymm6
    vaddpd %ymm9,%ymm8,%ymm8
    vaddpd %ymm2,%ymm0,%ymm0
    vaddpd %ymm6,%ymm4,%ymm4
    vaddpd %ymm8,%ymm0,%ymm0
    vaddpd %ymm4,%ymm0,%ymm0   # now ymm0 holds 4 partial sums
    vextractf128 $1, %ymm0, %xmm1  # grab the high 128 bits (lanes 2,3)
    vaddpd %xmm1,%xmm0,%xmm0       # add to low 128 (lanes 0,1) -> 2 doubles
    vhaddpd %xmm0,%xmm0,%xmm0      # horizontal add -> 1 double, now in xmm0 = return
    vzeroupper                     # good hygiene: avoid AVX/SSE transition stalls
    ret

    .section __TEXT,__const       # (Linux: use  .section .rodata  instead)
    .p2align 3
Lc: .double 1.0000001            # tiny value: accumulators grow slowly, never overflow to inf
driver.ctimes the kernel and prints GFLOP/s
// driver.c — calls the asm kernel, measures wall-clock, reports GFLOP/s.
// clock_gettime docs: https://man7.org/linux/man-pages/man2/clock_gettime.2.html
#include <stdio.h>
#include <stdint.h>
#include <time.h>

// Implemented in fma_kernel.s. Returns a scalar so the loop isn't optimized away.
extern double fma_kernel(uint64_t iters);

int main(void) {
    // ~2 billion loop iterations keeps the kernel running ~1s — long enough
    // to swamp timer noise, short enough to stay in single-core turbo.
    uint64_t iters = 2000000000ULL;

    struct timespec t0, t1;
    clock_gettime(CLOCK_MONOTONIC, &t0);
    double sink = fma_kernel(iters);       // the timed region
    clock_gettime(CLOCK_MONOTONIC, &t1);

    double secs  = (t1.tv_sec - t0.tv_sec) + (t1.tv_nsec - t0.tv_nsec) * 1e-9;
    // 10 accumulators * 4 fp64 lanes * 2 FLOPs(mul+add) = 80 FLOPs per iteration
    double flops = (double)iters * 80.0;

    printf("ignore: %g\n", sink);   // forces 'sink' to be used
    printf("time:   %.4f s\n", secs);
    printf("GFLOP/s (1 core): %.1f\n", flops / secs / 1e9);
    return 0;
}

Build & run

You're on macOS with an Intel core, so clang assembles the hand-written .s file and links it with the C driver in one command:

$ clang -O2 -mavx2 -mfma driver.c fma_kernel.s -o peak_fma
$ ./peak_fma

Expected output (numbers vary with turbo/thermals):

ignore: 3.2e+08
time:   0.83 s
GFLOP/s (1 core): 74.9
Reading the result. ~75 GFLOP/s on one core ≈ 4.7 GHz × 16 FLOPs/cycle — you're seeing single-core turbo × the exact "16" from tab 02, in the flesh. Multiply by 8 cores and you'd approach the 294 GFLOP/s ceiling (real all-core runs fall a bit short: turbo drops and heat rises). Against your scalar engine's ~2 MFLOP/s, this one core is ~37,000× faster — the entire gap this project exists to close.

Things to try

To make the hardware lessons tangible, change one thing at a time and re-run:

  • Delete accumulators. Cut the loop from 10 vfmadds to 1 (and fix the reduction). Watch throughput fall to ~¼ — that's the 4-cycle latency no longer being hidden.
  • Switch to fp32. Use vfmadd231ps and 8 lanes/register; the GFLOP/s roughly doubles, because the same 256-bit unit now packs 8 lanes instead of 4.
  • Go multi-core. Launch the kernel on N threads (e.g. OpenMP) and watch total GFLOP/s scale toward 294 — then dip as all-core turbo throttles under sustained load.
